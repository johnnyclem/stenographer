# Changelog

All notable changes to this project are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/).

## [1.0.0] - Unreleased

1.0 makes the truth ledger's guarantees hold in the default configuration, or states where they stop: agents draft and people sign (MCP tool profiles, server-bound identity), the ledger is append-only and hash-chained with a `verify` command, ingestion is idempotent across restarts, and wiki sync carries every state change in a versioned, hash-chained format. It adds a pre-dispatch gate (a Claude Code `PreToolUse` hook) and OpenAPPA integration. `STENO-T-NN` (truth ledger, objections, delivery) and `STENO-IDX-NN` (ingestion, extraction, retrieval, REST) refer to the findings of the suite 1.0 audit.

**Breaking**, **Security** and **Added** describe what changed. Every entry under **Breaking** is a breaking change, and so is every **Security** entry marked *Breaking*; upgrade steps for all of them are in [MIGRATION.md](MIGRATION.md). **Fixed** lists the defects 1.0 closes, by finding id. Most are closed by a change described above.

Not fixed in 1.0: STENO-T-21 (the notary secret lives in the process the agent's MCP host spawns; the README's threat model states that boundary), and the remainder of STENO-IDX-29 (the unused `sessions` table, session scope in `get_relations` and entity counts, and type-checking `test/` in lint).

### Breaking

**Runtime and package**

- **Node.js 22 or newer.** `engines.node` is `>=22` (Node 20 reached end of life in April 2026). CI runs Node 22 and 24. `@types/node` is `^22`.
- **`stenographer init` is removed** (STENO-IDX-29). It printed two lines, one of them an unscoped `npx stenographer` command that doesn't run this package, and set nothing up.
- **Dependencies:** `zod` `^3.25.28` (was `^3.22.0`). `zod-to-json-schema` is now a direct dependency (it was already installed through `@modelcontextprotocol/sdk`).

**MCP tools: profiles, identity and arguments**

- **MCP tool profiles, `agent` by default** (STENO-T-01, STENO-T-02). `stenographer start` now serves one of two profiles. `--profile agent` (the default) serves read tools, `propose_tombstone`, `assert_uv` and a `resolve_uv` that refuses any resolution that would mint a TB. `--profile operator` serves the judicial and destructive tools: `sign_proposal`, `dismiss_proposal`, `override_tombstone`, `file_ruling`, `rule_on_objection`, `assert_tombstone`, `import_wiki_entries`, `export_wiki_entries`, `backfill_legacy_tombstones`. Calling an operator tool on an agent-profile server is an error. In the operator profile, `sign_proposal` is the notary act: it signs agent drafts too.
- **Notarization is the default for agents; `requireNotary` is removed** (STENO-T-01). In the agent profile no MCP path mints an active TB without a person. `StenographerConfig.requireNotary` is gone. `--require-notary` is still accepted and does nothing. `--allow-agent-assert` (`allowAgentAssert`) is the single-user opt-out: the agent profile then serves `assert_tombstone`, signed by the agent identity. (`resolve_uv` minting from command evidence went away with self-signing command evidence; see **Truth ledger**.)
- **Identity is bound by the server in the agent profile** (STENO-T-18). Agent tools no longer accept `author`, `signedBy`, `proposedBy`, `dismissedBy` or `agentSessionId`; passing one is a validation error. Writes carry `--agent-identity` (`agentIdentity`, default `agent:<MCP clientInfo name>`) and the server's session id.
- **Engine write methods validate identities** (STENO-T-02, STENO-T-18). `signProposal`, `notarizeProposal`, `dismissProposal`, `overrideTombstone`, `fileRuling` and `ruleOnObjection` require a person. `draftTombstone`, `assertTombstone`, `assertUv` and `resolveUv` take a person or an agent. With a signer registry, identities must be listed in one of those roles and resolve to the registry's spelling. Without one, they are canonicalized (trimmed, NFC). They throw `IdentityError` (a `TruthWriteError`; REST answers `422`). `TbInputSchema` canonicalizes `signedBy` the same way.
- **Contempt of corpus compares canonical identities and checks every actor** (STENO-T-19). Identities compare after NFKC normalization, removal of invisible characters, trimming and case-folding. Session ids are trimmed. `resolveUv` checks the signer as well as the resolver, against the target's author, TB signer and the drafter of the proposal it was signed from. The author, signer or drafter of a TB can no longer refute a contest against it. `Stenographer.ruleOnObjection` refuses a ruling from the session the objection was raised against.
- **Reserved and malformed identities are rejected on every public write path** (STENO-T-24). `migration` and `detector:*` are refused as author and as signer everywhere except the backfill and the detector paths (`addProposal`). Identities containing control characters are refused.
- **Strict tool arguments** (STENO-T-23). Every tool's arguments are parsed with a strict zod schema before dispatch: unknown arguments, values outside an enum and wrong types are rejected with a validation error, and numeric limits are clamped (`list_objections` `limit: -1` returns 1 objection, not all of them). The advertised `inputSchema` is derived from the same schema (`additionalProperties: false`). `file_ruling` rejects any `kind` other than `strike`, `promotion` or `contempt`, and so does `TruthLedger.fileRuling`. Before, an unknown kind was filed as contempt and minted a TB. `TruthLedger.getTruth` throws `TruthWriteError` on an unknown filter instead of running invalid SQL.
- **Proposal dedupe no longer crosses authors** (STENO-T-26). `addProposal` returns an existing open proposal only if it has the same kind, target, author and notary requirement. `propose_tombstone` no longer hands an agent another author's proposal. When it dedupes into the agent's own open draft it says so (`dedupedInto`) and does not raise the draft again.
- **Terminal notary confirmation** (STENO-T-20). `stenographer notarize` asks you to type back a random code it prints on the terminal. It no longer uses the last four characters of the id you passed. `runNotaryCLI` takes an optional `NotaryIO` third argument.
- **Objection text no longer tells the objected agent to rule** (STENO-T-02). Channel and webhook objection text now says a person rules on it with `rule_on_objection`.
- **MCP annotations:** `export_wiki_entries` is no longer `destructiveHint`; both wiki tools are `idempotentHint`.

**Truth ledger**

- **Ledger status is derived from links, and the ledger is literally append-only** (STENO-T-06). A TB, UV or proposal's status is a fold over its inbound links on a lattice (TB active < contested < overridden; UV open < verified < refuted; proposal open < dismissed < signed; `strikes` makes an entry struck). No write updates a stored entry any more. Stored bodies no longer carry `status`; the `body.status` you read is the derivation. A TB that was overridden stays overridden when another contest against it is refuted. A body imported from the wiki keeps the status the line carried, which can hold the entry at a terminal status (overridden, verified, refuted) but not set any other. An imported UV's `contests` field now creates its `contests` link. Because links now decide status, an imported line keeps only the links about itself: links into it, its UV contest, and its TB's `supersedes` (and `signs` of a proposal this ledger doesn't hold). A line can no longer carry an `overrides` or `strikes` link at a local entry.
- **Dismissal is an appended ruling** (STENO-T-06). `dismissProposal` appends a `RULING` of kind `dismissal` (opinion: the reason) with a new `dismisses` link, instead of rewriting the proposal. The proposal's `dismissedBy` and `dismissReason` are read back from that ruling. `dismissProposal` takes an optional fourth `ctx` argument. New in the types: link type `dismisses`, ruling kind `dismissal`, entry type `MARKER` and `MarkerBody`.
- **Hash-chained ledger and a one-time migration** (STENO-T-25). Every entry stores `prevHash` and `hash = sha256hex(JCS(entry))` (RFC 8785), in insertion order. `truth_entries` gains `seq`, `prev_hash`, `hash` and `appended_links`, and a `truth_meta` table records the chain version. A pre-1.0 ledger is chained on first open (as schema migration 4; `stenographer verify` does the same), as it is, behind a `MARKER` (`chained-at-migration`) that lists the cached statuses derivation corrected. A pre-1.0 stenographer writing to a 1.0 database now fails verification.
- **`stenographer start` verifies the ledger and refuses to serve one that fails.** `--skip-verify` serves it anyway. `stenographer notarize` refuses to sign onto a ledger that fails.
- **Submitted `command` evidence is recorded as `claimed-command` and never self-signs** (STENO-T-01, STENO-T-25). `command` is reserved for checks stenographer executed, and 1.0 ships no runner, so every `resolveUv` that mints a TB now needs a person's `signedBy` and files a promotion ruling. With `--allow-agent-assert`, `resolve_uv` can no longer mint from command evidence under the agent identity (`assert_tombstone` still works there). `EvidenceSchema` accepts `claimed-command` and turns `command` into it.
- **One admission check for every ledger write** (STENO-T-03). `TruthLedger` validates each entry before it is appended, whichever path it came from: accountable (and, off their own paths, non-reserved) author and signer, a body of its type's shape, and only links its type writes, at entries of the type the link means. Library code that appended unusual entries through the ledger's public methods may now get a `TruthWriteError`.

**Team wiki: truth format v2**

- **Wiki truth format v2** (STENO-T-07; normative spec in `spec/truth-format/`). A wiki file is one ledger's append-only, hash-chained stream: every line carries `schemaVersion: 2`, `seq`, `prevHash` and `hash` (SHA-256 of the line's RFC 8785 form without `hash`). Status changes travel as appended `TRANSITION` lines (`target`, new `status`, `cause: {kind, ref}`), and the addenda and strike rulings that cause them travel as `ADDENDUM` and `RULING` lines. A TB or UV line's `status` is its status when written; a reader's current status is the latest TRANSITION's. `struck` is a status. `x-steno.links` holds only the links the entry's own write created, plus `ledgerHash`. v1 lines are still read. Removed: `entryToWikiLine`, `wikiLineToEntry`, `WikiEntryLine`, `TruthLedger.getExportableEntries`. `TruthLedger.importEntry` takes `(entry, links, opts)`.
- **Wiki export only appends, one writer per file** (STENO-T-05). Exporting into a file appends, in one write, the lines of this ledger's stream the file doesn't hold. A file holding anyone else's lines, or an edited line, is refused and left untouched. Export never truncates. `since` is replaced by `sinceSeq` (exports report `lastSeq`). `since` remains as a deprecated alias that returns the stream from the first line written after it.
- **Wiki import is one transaction, validated like a live write** (STENO-T-03, STENO-T-09). Every line is decoded, the chain is checked, and each entry is appended through the ledger's admission check. If any line fails, nothing is written and every failing line is reported. `ImportResult` is now `{committed, inserted, unchanged, derived, proposals, conflicts, held, errors}`. Anonymous or reserved identities, evidence-less TBs, unmatchable literals, edited lines and broken chains are errors. A TB lands as truth only when signed and verifiable (a hash-chained v2 line, signed by someone `--signer-registry` lists, if configured). Unsigned TBs, v1 TBs, unlisted signers, unknown statuses or values (fail closed) and conflicting lines become reconciliation `PROPOSAL`s that need a notary, filed once per line. Overrides, strikes and rulings from the wiki apply only from a person the registry allows; without a registry, they apply only to entries that came from the wiki, and one aimed at a TB or UV this ledger made itself is held. Resolutions meet the contempt rule. Anything else is held, not applied. A wiki line can no longer sign or dismiss a local proposal.
- **Proposal intake reads the suite PROPOSAL envelope** (truth format v2): `{schemaVersion: 2, seq, type: "PROPOSAL", id, ts, author, kind: "tb"|"uv", draft, targetRef, signal: {source: "compaction-candidate"|"agent"|"detector:<name>"}, prevHash, hash}`. Envelope lines are hash-checked and chained, and filed once per id whatever became of the proposal; envelopes that share a `targetRef` are each filed. Unknown `signal.source`, evidence and `verifyBy` kinds are kept and listed under `meta.intake.unknown` rather than refused. Blank lines are skipped and counted in error line numbers. `TruthLedger.addProposal` takes an optional third argument, `{reuseOpen: false}`, to file without reusing an open proposal for the same target. Tombstone drafts keep their `literals` (both dialects). The older dialects are still read.
- Wiki paths are confined to a wiki directory, and the tools take `file` instead of `path` (STENO-T-04); see **Security**.

**Objections**

- **Objections read only what a tool call asserts** (STENO-T-12). Before, every string in every tool call's input was scanned except keys starting with `old`. Now only asserting fields are read. These are Write `content`; the new side of Edit, MultiEdit and NotebookEdit; the parts of a shell command that write (environment assignments, redirected `echo`/`printf`/`cat` and heredocs, the replacement side of an in-place `sed`/`perl` `s///`, `bash -c` scripts, the command a `find`/`fd` `-exec` runs, `jq`/`yq`/`sort`/`uniq`/`cut`/`head`/`tail` whose output goes into a file (redirected, `yq -i`, `sort -o`, piped into `tee` or `sponge`), and other commands as written); and the added lines of `apply_patch`. Tools stenographer doesn't know are read through content-like field names (`content`, `new_string`, `new_str`, `file_text`, `code`, …; `patch`/`diff` by their added lines). Read, Grep, Glob, WebFetch, WebSearch, TodoWrite and Task inputs, shell searches (`grep`, `rg`, `find`, …), `git` and `gh` commands (commit messages included), `echo` without a redirect and `sed` without `-i` no longer raise objections.
- **The literal matcher works by clause** (STENO-T-12). A mention of the replacement value now skips only its own clause, not the whole line. A clause ends at `;`, `&&`, `||`, `//`, ` # ` or the start of another assignment, so `LOG_BUDGET = 30; MAX_RETRIES = 100` now objects. Negated and past-tense mentions ("do not set LOG_BUDGET to 30", "we removed legacyRateLimiter", "LOG_BUDGET was 30", "the old LOG_BUDGET of 30") no longer object. Subjects split acronyms (`maxHTTPRetries` matches `MAX_HTTP_RETRIES`), and an identifier literal now matches after a `.` (`this.legacyRateLimiter`). For a line over 500 characters, the quoted transcript line is an excerpt around the value instead of the line's first 500 characters. Only the first 1,048,576 characters of each text are scanned. Matching is linear in the text (each line is located once, not once per occurrence of a dead value on it), and the live scan reads each message for at most 2 s (`SCAN_BUDGET_MS`): past that, the rest of the message is not read and a note goes to stderr.
- **Objections are unique per session** (STENO-T-14). The `objections` table's unique key is `(session_id, message_id, tb_id, dead)`, not `(message_id, tb_id, dead)`. An existing table is rebuilt with the new key, rows kept, the first time a 1.0 stenographer (schema migration 4, or `stenographer gate`) opens it.
- **Startup replay never delivers objections, in any mode** (STENO-IDX-02, STENO-T-11). Before, only `catchup` forced shadow. Now, in `live`, `daemon` and `watch` too, whatever a log held when stenographer started is recorded as shadow, and only lines appended afterwards (or logs that appear afterwards) are delivered.
- **Delivery retries per objection, with backoff and dead-lettering** (STENO-T-15). Transient failures (network, 5xx, 408, 429) back off from 15 s, doubling up to an hour. A permanent refusal (other 4xx, 3xx) or the 8th failure dead-letters that objection for that receiver, and later objections are delivered anyway. Before, retries were every 15 s forever, in order, so one refused objection blocked every later one. A batch refused as a whole is retried one objection at a time, and a partial webhook batch is sent once its oldest objection has waited 5 minutes. New per-sink settings: `maxAttempts`, `retryBaseMs` and `maxBatchDelayMs`.

**Ingestion and session identity**

- **Ingestion resumes from a checkpoint instead of re-reading the log** (STENO-IDX-01). Each log's position is stored in the new `ingest_checkpoints` table, in the same transaction as each message and everything derived from it. A restart no longer re-indexes a log from byte 0. Use a fresh state path to rebuild an index on purpose. A detector proposal the ledger refuses (for example one quoting a lone surrogate, which can't be hashed for the chain) is logged and skipped in its own savepoint; the line is still indexed.
- **Decision and tombstone ids are deterministic** (STENO-IDX-01). They were `decision_<ms>_<random>` and `tombstone_<ms>_<random>`. They are now `decision_<hash>` and `tombstone_<hash>`, derived from the source message, the extractor and the captured text.
- **Message ids for id-less formats changed** (STENO-IDX-26). `openai`, `anthropic` and `generic` lines without an id used `msg_<32-bit FNV of the line>`. They now use `msg_<128-bit hash of log path, byte offset, line>`.
- **Session ids come from the harness or the log name, never the clock** (STENO-IDX-10). In every mode, a message's session is the id its log line records (Claude Code's `sessionId`) or else the log's basename (`<name>.jsonl` → `<name>`). Objections carry it, and so does `meta.session_ids`, which smallchat's messenger routes by. Before, `live`, `daemon` and `catchup` minted `session_<ms>` on each start and overwrote the adapter's id with it, so no objection could be routed. In file modes the latest such id is the query scope (`getSessionId()`, session-scoped tools), and it is stored with the checkpoint. `Tailer` defaults its session id to the log basename and keeps an adapter-parsed one.
- **State databases run in WAL mode and carry a schema version** (STENO-IDX-01). `PRAGMA user_version` is migrated in place on start. One ordered runner covers the whole file: the index tables (versions 1–3) and the truth layer (version 4: the hash-chained ledger, per-session objections and delivery state). A database written by a newer stenographer is refused instead of opened, by `start`, `notarize`, `proposals`, `verify` (exit 2) and `stenographer gate` (its `--on-error` decides) alike.
- **Format auto-detection matches on any sampled line** (STENO-IDX-05), not only the first, and waits for the first complete line of an empty log. `detectAdapterFromLines` keeps its JSONL fallback. The new `matchAdapterFromLines` returns `null` when nothing matches.
- **`Tailer` follows the path like `tail -F`** (STENO-IDX-03, STENO-IDX-04, STENO-IDX-20, STENO-IDX-28). In follow mode it no longer throws on a missing file: it waits for the file. It emits only newline-terminated lines, holding back a partial last line. The `message` event gets a second argument (`IngestPosition`), and there are new `progress`, `adapter`, `reset` and `removed` events. `LogAdapter.parseLine` takes an optional `LineContext`.
- **Tool results are role `tool`** (STENO-IDX-08). A turn made only of `tool_result` blocks (Claude Code, Anthropic) becomes role `tool`, tagged `tool_result`. A turn with prose keeps its role and only its prose. Claude Code `isMeta` and slash-command records are tagged `meta`, `isSidechain` records `sidechain`, `isCompactSummary` records `compact_summary` (new optional `tags` on `ConversationMessage`, stored and returned).

**Extraction, embeddings and retrieval**

- **The state database is pinned to its embedder** (STENO-IDX-24). The embedder's identity (kind, model, width, version) is stored in the new `index_meta` table. A database opens only under the same embedder; otherwise `start()` throws `EmbedderMismatchError` naming both. `--reembed` (`reembed: true`) recomputes every stored message and truth-entry vector under the new one. A pre-1.0 database is adopted with a warning.
- **No silent fallback to hashed embeddings** (STENO-IDX-24). A transformer model that can't load is a startup error with instructions. `--embeddings auto` opts in to the fallback (loudly), and `auto` follows the embedder the database is pinned to. `createEmbedder` takes an options object.
- **`Embedder` has two new required members** (STENO-IDX-24, STENO-IDX-06), `identity` and `supersedeThreshold`. Custom embedders must implement them. `TransformerEmbedder.dimensions` is the model's output width (read at load), not a fixed 384.
- **The default supersede threshold depends on the embedder** (STENO-IDX-06): MiniLM 0.45, hashed 0.75 (was 0.45 for all). `supersedeThreshold` / `--supersede-threshold` still override it.
- **Extraction mines user and assistant prose only, one assertion per sentence** (STENO-IDX-07). Tagged records, tool output, system turns, code fences, quoted lines and harness blocks yield no decisions, corrections or entities. Fewer, different decisions are extracted from the same logs. `ExtractedStructure.corrections[].to` is now the corrected (current) statement and `from` what it replaces (`''` when unnamed). Before, `from` held the captured text and `to` was always empty.
- **`search_conversation` / `GET /graphrag` / `GraphRAGRetriever.search` return messages only** (STENO-IDX-16). Entity and path chunks are gone. Their evidence is in each result's `meta` (`matchedEntities`, `paths`), and `score` is a fused reciprocal-rank score, not a cosine. Neighboring messages move from an appended `Context:` block in `content` to `meta.neighbors`. `RetrievedChunk.type` is `'message'`.
- **Recent messages are ordered by ingest order** (STENO-IDX-17) (`messages.seq`), not timestamp.
- **Context frames budget every section** (STENO-IDX-14) and can omit entities or decisions that don't fit.
- **REST and MCP clamp `k` to 200** (STENO-IDX-13), `n` to 1,000 and graph depth to 5. `StateStore.searchSimilar` clamps `k` to 4,096.
- **Supersession proposals dedupe per (superseded, successor) pair** (STENO-IDX-12, STENO-IDX-22): `targetRef` is `<superseded>-><successor>`, no longer the superseded decision's id. In `watch` mode supersession matches across sessions.
- **Schema v3** (STENO-IDX-15, STENO-IDX-25): `messages` gains `seq`, `tags`, `tool_calls` and `importance_total`; `index_meta` is new. The vector table is rebuilt (one row per message window, cosine distance, partitioned by session) from the stored embeddings on first open.

**REST**

- **REST query parameters are validated** (STENO-IDX-11, STENO-IDX-13). A malformed parameter is a 400 instead of a silent default (`k=abc`, `n=0`, `depth=-1`, `include=` anything but `shadow`), as is malformed percent-encoding in a path (was a 500). Counts are still clamped. `limit` is now clamped to 1,000 and `budget` to 100,000.
- **REST notary bodies are validated like the operator profile** (STENO-T-23). `POST /proposals/:id/notarize` takes exactly `{notary, edits?}` and `/dismiss` exactly `{dismissedBy, reason}`, and `edits` takes only what `sign_proposal`'s `edits` takes in the operator profile (the draft's `claim`, `evidence`, `literals`, `assertion`, `basis`, `verifyBy`, `contests`). Any other field, a wrong type or a blank `reason` is a `400` before anything is written. Before, unknown `edits` keys were passed to the ledger, and a type error there came back as `422`. Malformed percent-encoding in the proposal id is a `400`, as on every other route (was a `500`).
- REST requires a bearer token and an allowed `Host` (STENO-IDX-11); see **Security**.

### Security

The authority-model changes under **Breaking** (tool profiles, server-bound identity, canonical identities, reserved identities and the terminal notary's code; STENO-T-01, STENO-T-02, STENO-T-18, STENO-T-19, STENO-T-20, STENO-T-24) close the audit's findings about agents minting or neutralizing truth over MCP. The README's "Notarization, identity and the threat model" states the boundary: they hold for an agent whose only access is an agent-profile MCP connection, not for anything that runs as the operator's user (STENO-T-21). The entries below are the other security fixes.

- *Breaking.* **REST requires a bearer token and an allowed Host on every route** (STENO-IDX-11). Before, a web page that rebinds its hostname to 127.0.0.1 (DNS rebinding) could read transcripts from the loopback-only daemon, and any local user could read them. Every request now needs `Authorization: Bearer <token>`, with `STENOGRAPHER_REST_TOKEN` or the token generated on first run into `<state dir>/rest-token` (mode 0600; its path is printed on startup). `--rest-insecure` drops the token requirement. A `Host` other than `localhost`, `127.0.0.1`, `[::1]`, `--rest-host` or a `--rest-allow-host` name gets 421, and a cross-site `Origin` gets 403. Notary routes need the token as well as `X-Notary-Secret`. `new RestServer(engine)` now takes `{token}` or `{insecure: true}`.
- *Breaking.* **Wiki files are confined to a wiki directory** (STENO-T-04). Before, `export_wiki_entries` and `import_wiki_entries` took any path, so a caller could overwrite the state database or read any file the server could. They now take `file`, a `.jsonl` name relative to the wiki directory (`--wiki-dir`, `StenographerConfig.wikiDir`; default `wiki/` next to the state file), instead of `path`. Absolute paths, `..`, symlinks that resolve outside the directory, names that aren't `*.jsonl`, anything but a regular file, files over 64 MiB, and the state file itself (hard links included) are refused, and the final open doesn't follow symlinks. Passing `path` is a validation error. `Stenographer.exportWikiEntries` and `importWikiEntries` take `file` too. The functions in `wiki.ts` no longer touch the filesystem (`readWikiFile` and `appendWikiFile` in `wiki-file.ts` do, confined).
- *Breaking.* **Delivery never follows a redirect** (STENO-T-16). A 3xx is a permanent failure. Before, fetch followed it with the body and `X-Channel-Secret`, past the loopback check, so a receiver could forward objections, proposal drafts and the channel secret to another host.
- *Breaking.* **Webhooks are signed per Standard Webhooks** (STENO-T-17). `webhook-id`, `webhook-timestamp` and `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">` replace `X-Stenographer-Signature: sha256=<hex HMAC of the body>`, on objection and proposal webhooks alike. A receiver that checks the signed timestamp can refuse a replayed delivery. `STENOGRAPHER_WEBHOOK_SECRET` must be at least 24 bytes (a `whsec_` secret once decoded).
- *Breaking.* **Sink URLs are redacted** (STENO-T-17) in logs, in `createSinkTransport` errors and in `propose_tombstone`'s `raisedTo`/`undelivered`: they show the scheme, host and port, plus `/…` when the URL has a path or query.
- **Notices escape control characters** (STENO-T-22). `formatObjection` and `formatProposalNotice` render C0/C1 controls, line separators and bidi overrides in agent-written text as visible escapes (`\u001b`, `\r`, …), and cap each objection line at 2,000 characters.
- **Tamper evidence for the ledger** (STENO-T-25). The hash chain and `stenographer verify` (see **Breaking** and **Added**) detect an entry, link or cached status edited in the SQLite file. Deleting the newest entries, or rewriting from some entry on and recomputing every later hash, is caught only by comparing the head hash with a copy kept elsewhere. The chain is not a signature: it doesn't show who wrote an entry.

### Added

**Commands and options**

- `stenographer verify [state-path] [--json]`: validates the hash chain and the link table, re-derives every status from links, and reports the first divergence and the head hash. Exit 0 intact, 1 integrity failure, 2 could not run.
- `stenographer gate`: a Claude Code `PreToolUse` hook that checks what a tool call asserts against active TB literals before it runs. `--mode enforce` denies a hit with the TB as the exhibit and files an objection. `--mode shadow` (the default) files a shadow objection and allows the call. TBs come from the state file (opened read-only) or a wiki file (`--wiki`). A person's ruling for a TB and an exact call (canonical call digest, `smallchat.call.v1`) is honored on retry. The other options are `--timeout-ms` (default 2000, below the hook timeout), `--on-error allow|deny`, `--tools` and `--log`.
- On `stenographer start`: `--profile`, `--agent-identity`, `--allow-agent-assert`, `--signer-registry`, `--wiki-dir`, `--skip-verify`, `--embeddings auto`, `--reembed`, `--supersede-threshold`, `--rest-allow-host` and `--rest-insecure`; `STENOGRAPHER_REST_TOKEN`. `--signer-registry` on `stenographer notarize`.
- Signer registry: a JSON allowlist of signers with roles `human`, `agent` or `detector`. It supports aliases and prefix entries such as `agent:*`, and operator paths check against it (MCP operator profile, REST notary routes, terminal notary), as does wiki import.
- `get_status` reports the profile, the bound agent identity, `allowAgentAssert`, the embedder and `objections.deadLettered`. `GET /status` reports the embedder.
- MCP tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`).

**Specs, integrations and fixtures**

- `spec/truth-format/`: the truth format v2 spec (normative prose), its JSON Schema (2020-12) and golden fixtures (valid, unknown-value, v1, routing and invalid lines, with expected outcomes), shipped in the package as `@stenographer/core/spec/*`. `test/truth-format.test.ts` rebuilds the fixtures from a real ledger and checks them against the schema and the codec.
- `integrations/openappa/`: an [OpenAPPA](https://github.com/archestra-ai/OpenAPPA) 0.30.0 battery for every MCP tool of both profiles (`mcp/stenographer/<tool>`). Transcript and ledger reads return results restricted to `self` and `suspicious` (`get_status` keeps the session's trust). Every ledger write except `propose_tombstone` needs a trusted session. Overrides, rulings, notarization, dismissals, wiki imports (a file can carry overrides and strikes) and the operator calls that sign with a person's name also need the `hitl` mark. The directory also holds `appa replay` traces for two root configs and an install guide for use next to OpenAPPA's claude-code battery. `npm run test:openappa` runs `appa describe --check`, with the built server's tool list as the session's tools, and `appa replay`; it skips when no `appa` binary is found (`APPA_BIN` names one). CI runs it. `test/openappa-battery.test.ts` fails when the battery and the served tool lists drift apart.
- `POST /appa/context`: an OpenAPPA context provider (consult protocol v1, `kind: "context"`). Given a proposed call's `{tool, arguments}`, it answers with the TB literals the call asserts (TB id, subject, dead and current values, claim, signer, author, status, the asserting argument and line) and the UVs contesting them. A call is read exactly as the objection detector and `stenographer gate` read it, so a search, a read, a commit message or the old side of an edit is never a hit. It takes OpenAPPA's canonical tool ids (`host/claude-code/Bash`, `mcp/<server>/<tool>`) as well as the harness's own names. Matching has a 1 s budget (`CONSULT_BUDGET_MS`); past it, the answer carries the hits found so far and a `note`. It is read-only and uses the REST bearer token. OpenAPPA's runtime also defaults to port 8787, so run the daemon beside it on another `--rest-port`.
- Test corpora: `test/fixtures/literal-corpus.json` (a golden false-positive/false-negative corpus for the literal matcher), `test/fixtures/extraction-corpus.json` (46 labeled turns; CI floors precision 0.95 and recall 0.90), `test/fixtures/supersession-pairs.json` (threshold calibration), PreToolUse hook fixtures in `test/fixtures/gate/`, and a 0.x ledger in `test/fixtures/truth-ledger-0.x.sql` for the migration.
- `test/release.test.ts` keeps the reported server version, README badges, Node floor, CI matrix and CHANGELOG heading in step with `package.json`, and keeps unscoped `npx` names out of the docs.
- Dev dependencies `ajv` and `ajv-formats`, to validate the fixtures against the JSON Schema in tests.

### Fixed

**Truth ledger and notarization**

- Agents can no longer mint an active TB without a person over MCP: `sign_proposal` with edits, `resolve_uv` with `mintTombstone` or a verified contest, `file_ruling` with an unknown kind, `import_wiki_entries` and `assert_tombstone` are absent from the agent profile or refused by it (STENO-T-01).
- Agents can no longer override, strike or dismiss human-signed TBs, or overrule objections raised against themselves (STENO-T-02).
- An MCP caller can no longer sign as any person: agent-profile identity comes from the server, and operator paths check names against the signer registry when one is configured (STENO-T-18).
- `Alice`, ` alice ` and `ａｌｉｃｅ` can no longer corroborate each other, and a resolver can no longer promote a contest by naming the contest's own author as `signedBy` (STENO-T-19).
- The terminal notary can no longer be satisfied by a script that knows the proposal id (STENO-T-20). A program that reads the terminal still can; see the threat model.
- `migration` can no longer be used as an author outside the backfill (STENO-T-24).
- `propose_tombstone` no longer returns another author's proposal and drops the agent's draft (STENO-T-26).
- UV proposals whose draft carries `contests: null` (wiki reconciliation, short-hand and smallchat intake) can be signed. Signing edits may set `contests: null` to drop a contest (STENO-T-08).
- `get_truth` with an unknown `truthFilter` returns a validation error instead of `no such column: undefined`, and negative limits no longer return everything (STENO-T-23).
- Refuting a contest no longer returns an overridden TB to active (STENO-T-06). Before, a TB contested twice, overridden by one verified contest, came back as active truth, and objected again, when the other contest was refuted. The same happened when a force-overridden TB's contest was refuted. Existing ledgers are corrected on migration.

**Team wiki**

- Wiki import no longer writes entries verbatim (STENO-T-03): a line authored by `system`, a TB with no evidence, or a made-up status no longer lands as active truth.
- `export_wiki_entries` and `import_wiki_entries` can no longer overwrite the ledger or read any file the server can (STENO-T-04).
- A full wiki export no longer truncates the file and drops teammates' lines (STENO-T-05).
- Strikes, overrides, contests and resolutions now reach teammates' ledgers, and re-importing a file after them raises no conflicts, files no duplicate proposals and mints no second TB (STENO-T-07).
- One bad line no longer leaves a partial import and an exception (STENO-T-09): the file is rolled back and the result lists every bad line, including an entry that can't be hashed (for example, one with a lone surrogate).
- Imported entries are embedded, and entries without an embedding get one when search or the verification queue reaches them, so `search_truth` no longer ranks team truth at relevance 0 (STENO-T-10).

**Objections and delivery**

- Restarting `live`, `daemon` or `watch` in `deliver` mode no longer pushes objections on historical messages as if they were live (STENO-T-11, STENO-IDX-02).
- Searching for a dead value, committing its removal, or saying not to use it no longer raises an objection. `LOG_BUDGET = 30; MAX_RETRIES = 100`, `ENABLE_CACHE=false; DEBUG=true` and `MAX_HTTP_RETRIES = 5` (subject `maxHTTPRetries`) now do (STENO-T-12).
- Objection scanning no longer stalls indexing on large messages (STENO-T-13). Every active literal compiles into one matcher per ledger generation. Each text is read once, the settled literals are fetched once per scan instead of once per literal, and nothing is re-split or recompiled per literal. In the test suite, 1,000 literals against a 100 KB Write scan in about 10 ms. The same test took about 660 ms before, and the test fails above 150 ms.
- The same assistant line in a second session is objected to there too (STENO-T-14). Before, a message id from an adapter without native ids collided across sessions, and the second session was never warned.
- One objection a receiver refuses no longer stops delivery of every later objection to that receiver (STENO-T-15).
- A shadow objection no longer silences the first live one in its session (STENO-IDX-02, STENO-T-11). Lines a log held at startup are scanned in shadow, and so are the gate's objections in shadow mode. Because counsel doesn't repeat a pending objection, the agent asserting the same dead literal again, live, was never objected to. In `deliver` mode only a delivered pending objection (or an overruled one) now counts as already said.
- Objections from `live` and `daemon` mode reach the Claude Code session that raised them through smallchat's messenger (STENO-IDX-10).
- A redirecting receiver can no longer send objections, proposal drafts and the channel secret to another host (STENO-T-16).
- A captured webhook can't be replayed as a fresh one to a receiver that checks the signed timestamp, and webhook tokens in URLs no longer reach the agent or the logs (STENO-T-17).
- A drafted claim can no longer hide itself in the notary's terminal behind ANSI conceal codes, carriage returns or bidi overrides (STENO-T-22).

**Ingestion**

- A restart no longer inverts supersession chains, duplicates decisions, tombstones, proposals or migration TBs, or re-counts entity references (STENO-IDX-01).
- A line written in more than one chunk is no longer dropped (STENO-IDX-03).
- Deleting a tailed log no longer crashes the process with an unhandled rejection (STENO-IDX-04). `watch` mode drops that session, and `live` mode waits for the log to reappear.
- A log created empty is no longer locked into the JSONL adapter. Detection waits for its first line (STENO-IDX-05).
- Lines appended during the startup catch-up are indexed right away, not at the next write (STENO-IDX-19).
- Rename rotation, atomic replace and truncate-and-rewrite are followed (STENO-IDX-20). The old file is drained first. A rewritten file is read from the top instead of from a stale offset.
- `watch` mode starts exactly one tailer per new file, and `stop()` stops every tailer it started (STENO-IDX-21).
- Identical id-less lines ("continue", "ok") stay separate messages (STENO-IDX-26).
- A UTF-8 BOM at the start of a log is stripped (STENO-IDX-27).
- `live` and `daemon` wait for a log that doesn't exist yet instead of exiting with ENOENT (STENO-IDX-28).

**Extraction and retrieval**

- Claude Code tool results (file reads, grep and test output), caveats and subagent prompts are no longer mined as the user's decisions and corrections (STENO-IDX-08).
- Patterns no longer match inside words ("will use", "factually", "autocorrection:"). "Use X instead of Y" records X, not "of Y". First-person tool narration isn't a decision. A sentence-initial "Actually, …" correction is kept. Polarity isn't read inside quotations, and first-person narration of the next step ("Let me X instead of Y") isn't a correction. On the labeled corpus (46 turns), precision went from 0.25 to 1.00 and recall from 0.60 to 1.00. It is a development set, not a benchmark; CI floors are 0.95 and 0.90 (STENO-IDX-07).
- An Anthropic log whose first turn is string content no longer loses its `tool_use` blocks when detection picks the OpenAI adapter: both chat adapters share one normalizer, and either reads `tool_calls`, content blocks and `created` (STENO-IDX-09).
- Under the hashed embedder, unrelated decisions no longer supersede each other (STENO-IDX-06).
- An offline start, or a mistyped `--embeddings`, can no longer mix two embedding spaces in one database (STENO-IDX-24).
- In `watch` mode a decision reversed in a later session is closed. When logs replay out of time order, the newer version wins (STENO-IDX-12).
- In `assert` mode a second successor of one decision gets its own proposal. Signing every proposal, in any order, leaves one current version (STENO-IDX-22).
- `get_context_frame` stays within its budget in every section and keeps the newest message (STENO-IDX-14).
- GraphRAG fuses vector, entity and recency ranks instead of ranking fixed-score entity and path chunks above messages. Neighbors come from the same session. Its vector step uses the persistent index (STENO-IDX-16).
- `get_recent_messages` returns the last lines of logs without timestamps (anthropic, openai without `created`) (STENO-IDX-17).
- Tool-call-only turns are embedded as their calls (name and arguments) instead of empty text, and text with no features gets no vector, so it no longer scores 0.5 against every query under hashed. Scores are cosine similarity for vectors of any length (STENO-IDX-18).
- Session-scoped vector search no longer comes back empty when other sessions crowd the global top-k, and `k` above 1,024 no longer returns a 500 (STENO-IDX-13).
- Text past MiniLM's input window (a few hundred tokens; the rest was dropped) is searchable: long messages are embedded in overlapping ~1,000-character windows (at most 64) (STENO-IDX-25).
- Indexing is linear in session length (an indexed, embedding-free history read; statements prepared once; `synchronous=NORMAL` under WAL): 1k/4k/10k messages in 0.8/3.0/7.3 s on the test workload, against 2.2/19.7 s for 1k/4k before (STENO-IDX-15).
- Importance totals are stored and used by GraphRAG and context frames, as the README describes (STENO-IDX-23).

**REST**

- A web page can no longer read transcripts from the local REST API by DNS rebinding, and other local users can't read them without the token (STENO-IDX-11).

**Documentation and metadata**

- The README no longer overstates the truth layer's guarantees (STENO-T-25). It no longer says imports and direct writes can't bypass the override protocol, that wiki interop is lossless, that command evidence self-signs, or that stenographer never acts on a conversation; each claim now names what is enforced and where it stops. `docs/ecosystem/` and `wiki/stenographer.md` no longer say stenographer has no code-level ecosystem wiring, serves 11 MCP tools, or serves REST without auth.
- Docs and the CLI run the scoped package (`npx -y @stenographer/core …`), never `npx stenographer`, which is a different package (STENO-IDX-29).
- The `supersedeThreshold` JSDoc states the per-embedder defaults (it said 0.6) (STENO-IDX-29).
